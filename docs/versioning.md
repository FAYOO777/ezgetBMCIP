# ezgetBMCIP 版本号规则

## 当前基线

- 当前软件版本：`2.0.3`。
- 唯一版本源：仓库根目录 `Version.props` 中的 `EzGetBmcIpVersion`。
- 正式版、Legacy 和两个共享 Core 工程必须使用同一软件版本。
- 当前仍为本地开发支线；版本号变化不代表已经创建 Git tag、推送或正式发布。

## 递增规则

版本号按十进制逐位进位：

`2.0.0 → 2.0.1 → … → 2.0.9 → 2.1.0 → … → 2.9.9 → 3.0.0`

一次完整的软件修改批次只递增一次，不按修改文件数量、提交数量或测试次数重复递增。

## 需要递增软件版本的情况

只要修改会影响用户运行的软件，就必须在该批次完成时递增版本号，包括：

- 功能、业务逻辑、网络行为、安全恢复或诊断判断发生变化；
- 正式版或 Legacy 的界面、文案、交互、快捷键或可访问性发生变化；
- 性能、稳定性、兼容性或错误处理发生变化；
- 修改会被编译或打包进程序的配置、资源、依赖或运行时要求；
- 修复用户能够感知的软件缺陷。

## 不需要递增软件版本的情况

以下修改在不改变软件二进制文件和用户实际运行行为时，不递增软件版本：

- 版本规则、开发计划、交接说明和发布流程文档；
- 日志分析、测试记录、截图、支持包和实机测试证据；
- 只增加或调整自动化测试，但不修改产品代码；
- 代码注释、内部说明和不影响产物的格式整理；
- CI、本地构建或发布脚本的维护，前提是生成的软件内容和运行行为不变；
- 下载页、教程页等网站内容调整，前提是没有同时修改应用程序；
- 只读检查、问题分析和方案讨论。

如果一个批次同时包含文档改动和软件改动，则按软件改动处理，整个批次只递增一次。

## 修改与发布顺序

1. 确认本轮是否会改变用户运行的软件。
2. 如果会改变，在本轮完成前按规则更新 `Version.props`。
3. 同步更新对应版本的更新日志或发行说明。
4. 构建正式版和 Legacy，并运行相关测试。
5. 需要本地测试包时，使用与 `Version.props` 相同的版本执行 `publish-local-branch.ps1`。
6. 本地支线不得因此自动创建 tag、推送、上传或修改线上 `versions.json`。

## 当前下一版本

- 纯文档、测试记录或发布规则维护后仍保持 `2.0.3`。
- 下一次完成影响软件本身的修改后，版本升级为 `2.0.4`。
